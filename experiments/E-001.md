**The question.** Can a past task be re-run at the repository state it started from, with what its agent had then and nothing it could not have had, so that a paired test (the same past tasks run with and without a change, compared task by task) can run on past work?

## Hypothesis
For each kind of work (plans, research, built work), past tasks can be replayed faithfully, often enough to fill a paired test. Either outcome is a result: if replay works for a kind, the fair test (M2) uses past tasks for that kind; if it fails, M2 uses the brief's fallback for that kind (below). A kind may go either way independently of the others.

## Method
Two steps, in this order. Step 1 uses no runs; step 2 uses runs.

**Step 1 — the records check (no runs).** For each audited piece of past work, the Builder that runs this check (docs/PROJECT.md section 4), working in its own session with scripts and no helper sessions, tests three things, from the records and full git history only (`git fetch --unshallow` first in each repository; each session clones fresh):
- **F1, start state:** the commit the task started from is named by a record (a dispatch-log line, a review record's "at <commit>", a branch's base or a PR's base), and a worktree at that commit can be made.
- **F2, inputs:** everything the task read is present at that commit: the spec or request, the files its pack or brief names, the role file. Outside web pages read at the time count as missing: they cannot be restored to their state then, and neither Design check reads the web.
- **F3, brief:** the brief is recorded, or it can be rebuilt by a fixed template from files at that commit alone (the role file, the pack, and the task statement in the spec, stage or request). A rebuilt brief is marked "rebuilt"; nothing written after the start (later rounds, review records, the merged result) may be used to rebuild it.

**Which pieces (24, plus a rule-based addition).** One "piece" is one unit of work put to its check, as research/Q-008-memo.md §1.1 defines it. The pieces are taken from the samples Q-008 already drew by rule (§3, "Samples"), turned into pieces (a piece sampled twice counts once), in the order listed there, alternating the Service Desk (SD) and the operating model's repository (POOM):
- **Plans (8):** SD M3B, POOM S-007, SD M3C, POOM S-012r, SD after-glance, POOM S-015, SD desk-v2, POOM S-022.
- **Built work (8):** SD HD1, POOM S-017, SD M3B stage vt3, POOM S-023/24, SD M3E stage g5, POOM PR5, SD M3G stage qw1, POOM S-014.
- **Research (8):** in the order of Q-008 §2.1's tables, alternating the Service Desk's scripted path and Model-Lab: SD Q-001, ML Q-001, SD Q-002, ML Q-002, SD Q-004, ML Q-003, SD Q-005, ML Q-004.
- **Added by rule:** any other of the 19 research memos Q-008 counts whose memo states it used no web sources (ML Q-006 is one), so the research result does not rest only on memos that read the web.

**Step 2 — the replay runs (16 runs, plus up to 4 reruns).** From the pieces that pass F1–F3, take 8 in the order above, rotating plans, built work, research (3, 3, 2); if a kind runs short, its places go to the next kind in the rotation. For each:
1. Make the working directory: a copy of the repository holding only history up to the start commit, so later commits, review records and the merged result cannot be reached (a worktree inside the full clone is not enough: later history is readable from it).
2. **Replay run:** one helper on Opus 5.5 does the task unchanged: the original or rebuilt brief, the role file and pack as at that commit, no web.
3. **Check run:** one helper on Fable 5.1 judges the result as the piece's check did then (the checker's role file, pack and rules as at that commit). This is also the first judgement E-002 uses.
4. Test the run for:
   - **F4, no leak:** the transcript shows the replay read nothing absent from the start commit and no later history.
   - **F5, tools:** every script or check the task ran, runs at that commit.
   - **F6, completes:** the replay finishes and hands over work of the same kind and scope (the same files or sections).
   - **F7, checkable:** the check run reaches a verdict.

A run that fails F4 or F5 because of a fault in the set-up (not in the record) may be re-run once after the set-up is fixed, using the reserve; the failed run, its cause and the fix are reported.

## Measure
- **Records share, per kind:** pieces passing F1–F3, out of those audited; with how many briefs were recorded and how many rebuilt.
- **Run result, per kind:** runs passing F4–F7, out of those run.
- **Pool for M2, per kind:** the records share times the pieces of that kind Q-008 counts (plans 44, research 19, built work 80), as an estimate of how many past tasks the paired test could draw on.
- **Reported, not deciding:** each replay's verdict beside the piece's recorded round-1 verdict. It cannot decide: the original model is not recorded (Q-008 §5), the judge differs, and 8 pieces are too few. A large gap is reported with its likeliest cause.
- **Cost:** the tokens, tool uses and time each helper reports at return, per run, for M2's budget and the owner's token checkpoint.

## Sample
24 pieces audited, plus any added by rule (no runs). 8 pieces replayed.

**Runs.** One run is one helper session started for this check, on one piece, whatever it does (replays or judges); a session that errors still counts. The Builder's own session and its scripts are not runs. E-001 uses 16 runs (8 replay, 8 check) and at most 4 more for reruns: at most 20. E-002 uses at most 20. Together at most 40 of the 100 runs allowed through Design (docs/PROJECT.md section 8). Reruns not used are not moved to E-002.

## Exclusions
- Kinds other than plans, research and built work (documents put to the Critic, gate cases, other reviewed work, triage): the fair test starts with the three kinds V1 and V2 name; replay for a further kind is checked when it enters the test (docs/PROJECT.md section 8).
- Pieces Q-008 leaves out for having no recorded verdict (for example SD Q-003). A piece that fails F1–F3 is **not** excluded: it counts against its kind.
- The sample is drawn from Q-008's samples of returns, so it holds only pieces sent back at least once. First-time passes are rare (plans 2 of 44), and the records check concerns the records, not the verdict; the result states this.

## Deciding threshold
Set per kind, now:
- **Replay works** for a kind when at least half its audited pieces pass F1–F3, **and** at least 2 of its pieces are replayed, **and** every one of its replays passes F4–F7 (after at most one rerun for a set-up fault). M2 then runs that kind's paired test on past tasks, drawing only on pieces that pass F1–F3, and states the pool.
- **Replay fails** for a kind otherwise: fewer than half pass F1–F3, or fewer than 2 can be replayed, or any of its replays leaks, cannot run its tools, does not finish or cannot be checked. **This triggers the brief's fallback for that kind:** M2 compares new work with and without the change over the same period, and states the larger sample it needs (docs/PROJECT.md section 7, U2).
- A replay that passes with a rebuilt brief counts as working: in a paired test both arms get the same brief and only the change differs. The result reports how many replays used rebuilt briefs.

## Holdout use
None. The pieces used here are listed in the result, so M2 can keep them out of its held-back set and its test pool.
