**The question.** Can a past task be re-run at the repository state it started from, with what its agent had then and nothing it could not have had, so that a paired test (the same past tasks run with and without a change, compared task by task) can run on past work? And if the agent's brief was never recorded, can a brief rebuilt from the records stand in for it, for changes that leave the brief alone?

## Who does what
- **The Builder** runs this check exactly as registered (the experiment playbook): it does the records check in its own session with scripts, makes the working copies, and starts every helper session.
- **The Reviewer**, which did not run it, analyses the results against the thresholds below. The orchestrator records the Reviewer's verdict verbatim.
- The Builder may not re-run anything for a better answer (D-047). The only reruns are the set-up reruns defined under "Sample".

## Hypothesis
For each kind of work (plans, research, built work), past tasks can be replayed in one of two grades, and the result says which, for each kind:
- **Faithful replay:** the agent's own brief is on record. Such a replay supports a paired test of any change, including a change to briefs.
- **Template replay:** the brief is rebuilt by the fixed template below. Such a replay supports a paired test only of a change that touches neither the brief nor the template, for example to inputs handed over, the split of work, the AI model or the check. It is never called faithful.

Either outcome is a result for each kind and each grade: a kind that can be replayed in neither grade goes to the brief's fallback.

**Prediction, stated in advance.**
- **Research** will not be replayable in either grade. Nearly every past memo read outside web pages, which cannot be restored to their state then, and neither Design check reads the web. Research then goes to the fallback.
- **Plans and built work** will rarely reach faithful replay, because worker briefs are not recorded for conversation-started work (Q-008 §5). They may reach template replay.

## Method
Two steps, in this order. Step 1 uses no runs; step 2 uses runs.

### Step 1 — the records check (no runs)
The Builder fetches full history first (`git fetch --unshallow` in each repository; each session clones fresh). It then tests each audited piece on three things. Each verdict cites the record lines or commit it rests on (file:line, or the commit and path).

- **F1, start state.** A record names the commit the work started from. That is the commit the agent's working directory was at before it wrote anything:
  - a dispatch-log line's commit;
  - the base of the work's branch or pull request;
  - the parent of the work's first commit.

  A review record's "Reviewed … at <commit>" names the finished work, not the start. A piece whose only recorded commit is the reviewed one fails F1.
- **F2, inputs.** Everything the task statement, brief or pack names is present at the start commit: the spec or request, the files the pack or brief names, and the role file.
  - What else a conversation-started agent read is not recorded. F2 checks the named inputs only, and the result says so.
  - Outside web pages count as missing.
- **F3, brief.** The brief is graded as one of:
  - **recorded:** its text is on record, or a dispatcher script at the start commit builds it from files at that commit, so re-running the script gives the same text;
  - **rebuilt:** it is filled into the template below from files at the start commit alone;
  - **neither:** F3 fails.

  Nothing dated after the start may be used to rebuild a brief: no later rounds, no review records, no merged result.

**Which pieces.** One "piece" is one unit of work put to its check (research/Q-008-memo.md §1.1). Pieces come from the samples Q-008 drew by rule (§3, "Samples"). A piece sampled twice counts once. They are taken in the order listed there, alternating the Service Desk (SD) and the operating model's repository (POOM).

- **Returned pieces (24).** These are pieces sent back at least once. Every threshold below is set on these.
  - **Plans (8):** SD M3B, POOM S-007, SD M3C, POOM S-012r, SD after-glance, POOM S-015, SD desk-v2, POOM S-022.
  - **Built work (8):** SD HD1, POOM S-017, SD M3B stage vt3, POOM S-023/24, SD M3E stage g5, POOM PR5, SD M3G stage qw1, POOM S-014.
  - **Research (8):** in the order of Q-008 §2.1's tables, alternating SD's scripted path and Model-Lab (ML): SD Q-001, ML Q-001, SD Q-002, ML Q-002, SD Q-004, ML Q-003, SD Q-005, ML Q-004.
- **First-time-pass pieces (6, reported separately, not in the thresholds).** These show whether work that passed first time has thinner or fuller records.
  - **Plans:** SD HD1's plan and POOM S-027, the only two (Q-008 §2.2).
  - **Research:** SD Q-008 and SD Q-013, the scripted path's two (Q-008 §2.1).
  - **Built work:** the first SD unit in Q-006 §4's list with one round and a PASS, and the first POOM piece in Q-008 §2.3's list that passed in round 1, not counting the single-PASS PRs 25 to 31, which record no earlier round. Q-008 §2.3 does not say which piece passed in round 1, so the Builder cites the record lines (review file and line) that show each chosen piece's round-1 PASS, and that every piece before it in the list did not pass in round 1.
- **Web-free research (own stratum, reported separately, not in the "at least half" test).** These are the memos among the 19 that Q-008 counts whose memo states it used no web sources; ML Q-006 is one. The Builder counts them directly: it reads each memo's sources statement and cites the line. These memos are chosen because they are likely to pass F2, so mixing them into the returned-pieces share would inflate it.

### Step 2 — the replay runs
From the returned pieces that pass F1–F3, the Builder takes 8, rotating plans, built work, research (3, 3, 2). Within a kind it takes recorded-brief pieces first, in list order, then rebuilt-brief pieces.
- Research places go first to web-free memos that pass F1–F3, since no other research piece passes F2.
- A kind that runs short gives its places to the next kind in the rotation.

For each replay, in this order:
1. **The working copy.** The Builder makes a new, empty repository outside every full clone, fetches only the start commit into it from the full clone, and checks it out: `git init <copy>`; `git -C <copy> fetch --no-tags <full clone> <start commit>`; `git -C <copy> checkout --detach FETCH_HEAD`.
   - The copy then holds that commit and its ancestors only. The Builder checks this for every copy and records it in the result: `git -C <copy> rev-list --count HEAD` equals `git -C <full clone> rev-list --count <start commit>`, and `git -C <copy> cat-file -t <a commit later than the start commit that exists in the full clone>` fails; this second part is skipped when no such commit exists. A copy that fails this check is a set-up fault.
   - A worktree of the full clone is not used: later history is readable from it.
2. **The replay run.** One helper on Opus 5.5, with its working directory set to the copy. It gets the recorded brief, or the rebuilt brief from the template, plus the confinement paragraph below. It does the task unchanged.
3. **The leak, tools and finish tests (F4–F6), before any judging.**
   - **F4, no leak.** The helper's saved transcript holds every tool call it made (stored for each helper in the starting session's folder, `subagents/agent-<id>.jsonl`). F4 passes when no call:
     - reads, searches or runs a command on a path outside the copy;
     - fetches a web page;
     - runs a git command naming another repository.

     - **System paths allowed:** reading or running the tools the commands need under /usr, /bin, /lib and /etc (read only), and files the run itself creates in the system temporary directory (/tmp). Any other path outside the copy fails F4, including the rest of /home/user, /root (with ~/.claude) and other sessions' folders.
     - **A borderline call** (a path whose kind is unclear) is decided by the Reviewer, citing the transcript line, not by the Builder.

     If the transcript is missing, F4 fails by rule. This includes a helper started by a Builder that is itself a helper, whose transcript may be stored elsewhere or not at all.
   - **F5, tools.** Every script or check the task statement or brief tells the agent to run, runs in the copy.
   - **F6, finishes.** The helper ends and has produced the deliverable of the original's round-1 submission, of the same kind: a spec draft for a plan, a memo for research, a change to code or tests for built work. It changes at least one of the paths the original round-1 submission changed (from git), and none outside the role's write lane at the start commit.
4. **The check run, only if F4–F6 pass.** The Builder commits the replay's output in the replay copy as one commit on top of the start commit; if the replay committed its own work, its last commit is used instead. The Builder then makes a second copy the same way, fetching that commit. One helper on Fable 5.1 judges the result there, with the judge brief from the template in E-002.
   - **F7, checkable:** it returns a verdict line.
   - This is the first test-judge verdict E-002 uses.
   - A replay that fails F4, F5 or F6 is not judged.

**The brief-rebuilding template.** The Builder fills each `<…>` from files at the start commit only, and cites the source of each filled field in the result. Nothing else is added.

```
You are the <role id> (your role file: <role file path at the start commit>).

Your task: <the task statement, copied verbatim from the spec stage, request record or
dispatch record at the start commit — cite path:lines>.

Read first: <the files the role's context pack names at the start commit (governance/PACKS.toml
or its equivalent then), in the pack's order>; <the spec or request path>.

Hand back: <the deliverable of this kind, at the path the task statement names>, and whatever
the role file says a hand-back must contain.
```

**The confinement paragraph.** It is added unchanged to every replay brief, recorded or rebuilt. It is the only text a recorded brief gains. The repository's original absolute path, wherever the recorded brief uses it, is replaced by the copy's path, and nothing else is changed.

```
Work only in <copy path>. Do not read, search or run commands on any path outside it, do not
use the web, and do not run git commands that reach any other repository.
```

## Measure
For each kind, recorded-brief and rebuilt-brief results are reported separately.
- **Records share:** returned pieces passing F1–F3, out of those audited, by brief grade. The first-time-pass pieces and the web-free stratum are reported beside it, not added in.
- **Run result:** replays passing F4–F7, out of those run, by brief grade.
- **Pool for M2.** The records share (by grade) times the returned pieces of that kind: plans 42 (44 less 2 that passed first time), research 14 (19 less 5), built work 48 (80 less 32) (docs/PROJECT.md section 6). For research, the pool is instead the web-free memos counted directly that pass F1–F3. The pool covers returned pieces only. A conclusion drawn from it holds for work that was sent back, and the result says so for each kind.
- **Reported, not deciding:** each replay's verdict beside the piece's recorded round-1 verdict. It cannot decide:
  - the original worker's model is mostly unrecorded (Q-008 §5 finds two "Session: Opus 5.5" headers, in SD desk-v2 stage 1b, and none for these pieces);
  - the judge differs;
  - 8 pieces are too few.

  A large gap is reported with its likeliest cause.
- **Cost:** tokens, tool uses and time per run, as each helper reports at return, for M2's budget and the owner's token checkpoint.

## Sample
- **Records check:** 24 returned pieces, 6 first-time-pass pieces and the web-free stratum. No runs.
- **Replays:** 8 returned pieces.

**Runs.**
- One run is one helper session started for this check, whatever it does; a session that errors still counts. The Builder's own session and its scripts are not runs.
- E-001 starts at most 8 replay runs and at most 8 check runs.
- **A set-up rerun costs 2 runs:** a new replay and, if it passes F4–F6, its check. It is allowed only when:
  - F4 or F5 failed because of the Builder's set-up (a wrong commit fetched, a copy built wrongly), not because of the record;
  - the fault is found before the replay is judged;
  - the failed run is kept in the result with its cause and fix.
- The reserve is 4 runs, so at most 2 reruns. When 4 rerun sessions have been started, no more are allowed.
- **Hard cap:** E-001 starts at most 20 helper sessions, counted as started, whatever their outcome. E-002 starts at most 20. Together they start at most 40 of the 100 runs allowed through Design (docs/PROJECT.md section 8). Runs E-001 does not use are not moved to E-002.

## Exclusions
- **Kinds other than plans, research and built work** (documents put to the Critic, gate cases, other reviewed work, triage).
  - The test starts with the three kinds V2 names; section 8 has every kind "tested in turn".
  - This registration's rule: replay for a further kind is checked by a new registration when that kind enters the test.
- **Pieces Q-008 leaves out for having no recorded verdict** (for example SD Q-003). A piece that fails F1–F3 is not excluded: it counts against its kind.

## Deciding threshold
Set now, per kind, on returned pieces:
- **Faithful replay usable:** at least half the audited returned pieces pass F1–F3 with a recorded brief, **and** at least 2 recorded-brief replays are run, **and** every one of them passes F4–F7. M2 may test any change on that kind's past tasks, drawing only on pieces that pass.
- **Template replay usable:** otherwise, if at least half pass F1–F3 with a recorded or rebuilt brief, **and** at least 2 replays of the kind are run, **and** every one passes F4–F7.
  - M2 may test on past tasks only changes that touch neither the brief nor the template, with both arms on the same brief.
  - A change to briefs for that kind goes to the fallback.
- **Research:** judged on the web-free stratum alone. It is usable in a grade only if at least 2 web-free memos pass F1–F3 and at least 2 are replayed, all passing F4–F7.
- **Neither:** the kind goes to **the brief's fallback** (docs/PROJECT.md section 7, U2): M2 compares new work with and without the change over the same period, and states the larger sample it needs.
- **"Usable" means usable in part, not "enough".** E-001 reports each kind's pool. M2 then states the pairs it needs per kind. If a kind's pool is below that number, M2 uses the fallback for that kind and does not mix past and new tasks in one comparison.
  - For scale, my inference, not a figure section 6 states: section 6's "about 300 runs" for three kinds, at two runs per pair, is about 50 pairs per kind. By that, research (14 returned, fewer web-free) and plans (42) could not fill a test even if every piece were usable.

## Holdout use
None. The pieces used here, including those only audited, are listed in the result, so M2 can keep the replayed ones out of its held-back set and its test pool.
