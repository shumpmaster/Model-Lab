**The question.** For each kind of work, does one candidate change raise the first-time pass rate by enough that chance alone would give the gain at most 1 time in 40 (V1), when each new piece of work is done, or checked, both with and without the change, from the same starting point, at the same time?

## Who does what
The test runs in separate sessions, each started with only the repositories it may hold (S-001, "The sessions, and what each holds"). **The sheets repository** is the owner's new private repository for the held-back checks; it is held only by the sheet session and the judging session of each kind, never by a session that does or starts the work.
- **The Check author, blind (dispatch (a))** writes each kind's held-back check before that kind opens (Method, step 1). It is a helper of that kind's **sheet session**, a session the owner starts with the sheets repository only. Its pack folder is built there by the sheet lead from the files the per-task pack `S-001-holdout` allows (governance/PACKS.toml), as listed, with each file's SHA-256, in the manifest the Orchestrator records before dispatch (S-001, J8): experiments/E-003/check-author-extract.md and the existing check standards that file names, plus .claude/agents/check-author.md and the helper's brief. It never sees the change texts (experiments/E-003/C?-*.md; patterns are compared case-folded, as governance/checks/session_runner.py's `norm` does, so `C*.md` would also match the extract), S-001, this file, S-001's locked checks, or any arm's output. It returns the check's text to the sheet lead only and writes no file.
- **The Check author, normal (dispatch (b))** writes S-001's locked checks from the spec at stage 4, on its standing pack, as a helper of the Orchestrator's session; it never holds a held-back check.
- **The Builder** builds the harness (src/E-003/**, tests/E-003/**) and runs the work side exactly as registered, in the kind's **work session**, a session the owner starts with Model-Lab and the work repositories the kind's pieces come from, which wakes once a day to find new pieces (S-001, "What wakes the long-lived sessions") and pushes its branch before each turn ends: it makes the copies, applies the change text, starts every doer arm and research check, runs built work's locked checks, writes each output's neutral export, and records every run. Its harness also holds the three scripts the sheets-side leads run, each tested in Model-Lab with a stand-in sheet (S-001, J4): the judge-brief fill script, the transcript check and the export reader. It may not re-run anything for a better answer; the only reruns are those defined below. It never holds a sheet.
- **The sheet lead and the judging lead** are the Orchestrator's role, each acting in one sheets-side session alone: the sheet lead in the kind's sheet session, the judging lead in the kind's **judging session**, which the owner starts with the sheets repository only. They write only to the sheets repository. The sheet lead places the sheet and computes its fingerprint (Method, step 1). The judging lead checks the sheet against its fingerprint, fills each judge brief, starts each judge and records its verdict (Method, step 4). Each returns only the fixed-form blocks of S-001, J4 and J5, which hold no sheet text.
- **The Orchestrator**, in its own session, writes every brief and the first-message line for each session the owner starts, records each manifest, records the blocks the owner passes to it, records each set id and fingerprint in governance/HOLDOUTS.md, lands the Builder's records and exports once a week, each landing with a Reviewer's PASS as class R1 requires (S-001, "The landing's authority"), and runs K1's probe before the first sheet is written (S-001, K1). - **The owner** places the canary file in the sheets repository before any probe and gives its word only to each sheet session's lead (S-001, K1), starts the work, sheet and judging sessions, passes each lead's blocks to the Orchestrator's session, sends a wake message only where a session cannot wake itself (S-001, K7), answers a small sample (Method, step 5) through cards the Chief of Staff prepares, and rules at each review point (Sample).

It never receives a sheet's text, a filled judge brief or a judge's transcript; it receives the verdict record instead (S-001, J5).

## Hypothesis
Each change raises its kind's first-time pass rate over leaving things as they are:
- **C1, plans:** the writer reads the role file of the agent that will check its plan (experiments/E-003/C1-plans-read-the-check.md).
- **C2, built work:** the builder is handed the inputs that bear on its task by name (experiments/E-003/C2-built-named-inputs.md).
- **C3, research:** the source check returns a memo only for a fault it can show, not for a source it could not open (experiments/E-003/C3-research-check-what-it-can-open.md).

"No change helps" is an accepted result for each (decisions/questions/P-001-no-change-result.md). The test is sized for a 20-point gain; a smaller real gain will usually read "not shown" (S-001, "What the test can and cannot show").

## Method

### Step 1 — the held-back checks (before each kind opens)
- For each kind, the Check author writes one held-back check: a short list of pass/fail tests, each naming a fault that sends the work back, written from that kind's existing check standard at the time, as experiments/E-003/check-author-extract.md sets out. The standard is the Model-Lab copies of the plan check's, build review's or source check's role file (.claude/agents/critic.md, reviewer.md, source-checker.md) and the software playbook (docs/playbooks/software.md) only: a Model-Lab pack cannot hold another repository's files, and no research playbook file exists in either project.
- **The sheet's route** (S-001, "The sheet's route", J4 and J8):
  1. The Orchestrator records the pack's manifest from `S-001-holdout` at the commit it dispatches from, and J8's test passes on it. The owner starts the kind's sheet session with the sheets repository only.
  2. The sheet lead builds the pack folder from those files, each read from Model-Lab at that commit and checked against its SHA-256, in a new empty folder outside every clone and outside any folder that holds an instructions file (S-001, "The sheet's route"), and (only once it has read the K1 records the owner names and found every part refused and the canary not shown, S-001 K1) starts the Check author as a helper with the pack folder as its working directory.
  3. The Check author returns the check's text to the sheet lead only.
  4. The sheet lead runs the transcript check on the helper. A read, search or command outside the pack folder, or any web or network use, **voids** the check: it is not placed, and the kind does not open until the owner rules (one new sheet session, 1 run, or stop this kind).
  5. Otherwise the sheet lead writes the text unchanged as `holdouts/<set id>.md` in the sheets repository, computes its fingerprint (the SHA-256 of that file's bytes), commits and pushes it, and returns the fixed-form block (S-001, J4).
  6. The owner passes the block to the Orchestrator's session. The Orchestrator records it as reviews/E-003/<kind>/sheet.md and records the set id and fingerprint in governance/HOLDOUTS.md, with a ledger entry carrying `holdouts: changed` in the same change.
- No session that does or starts the work holds the sheets repository; no arm's copy, brief or export holds the check; no doer or checker under test sees it.
- Writing each is one run. A held-back check, once fingerprinted, is never edited during the comparison for its kind.
- A sheet session lost before step 5's push loses the check's text, which is held nowhere else: the owner starts a new sheet session, which writes a new check with set id n = 2 (1 run, counted in the kind's runs and reported); the lost one is never placed (S-001, K5).

### Step 2 — which pieces enter
A **new piece** is one unit of work put to its independent check (research/Q-008-memo.md §1.1): a plan's round-1 draft, a built stage's round-1 submission, or a memo's round-1 submission, which meets all of these:
- its task is dispatched after its kind's comparison opens, in a participating project (S-001, AC2) whose repository is public: today the Service Desk or Model-Lab, so the operating model repository's pieces do not enter and no export carries a private repository's tree (decisions/questions/P-001-build-gate-terms.md, term 7);
- for plans and built work: the worker's brief text, the commit it started from and the AI model it ran on are on record at dispatch;
- for research: the memo's round-1 submission commit, **and** the source check's brief text, the commit the check started from and the AI model it ran on, are on record at the check's dispatch (C3 acts on the check's brief, so the check's record is the one the arms need);
- "on record" means a record written at dispatch, before the piece's round-1 verdict: the brief-and-model record (M3) once it exists; the Service Desk's control files (reviews/<item>/_control/*.json, which hold `brief`, `model` and `source_tip`) for its scripted work; or a brief record by the Chief of Staff that holds all three. Model-Lab's docs/briefs/ held the brief text and a model line but no start commit when counted (experiments/E-003/output.txt, arrivals part 4); by the owner's ruling its brief records gain the starting-point field `start:`, and the Chief of Staff records each plan's and built piece's brief, start commit and model, and the source check of research started in a conversation, at hand-out until M3 is built (decisions/questions/P-001-build-gate-terms.md, term 9), so such a record qualifies when it holds all three, its `start:` naming the piece's start commit (for research, the source check's);
- it is of the kind under comparison;
- it is not part of this test (S-001's harness, its results, or a change being carried into the operating model).

Each eligible piece enters in dispatch order until the kind's number of pairs is reached or the owner stops the kind at a review point (Sample).

### Step 3 — the pair (in the work session)
- **When a pair starts.** At each daily wake, the work session lists the dispatch records added since its last scan and starts the pair of every eligible piece it finds (S-001, "What starts a pair"); a piece first found more than 7 days after its dispatch is not eligible, and is listed (Exclusions 6).
- **Plans and built work (C1, C2): two doer arms per piece.** The harness makes two working copies of the piece's start commit as E-001 step 2.1 does (a fresh repository holding that commit and its ancestors only, checked the same way). In one copy the brief is the recorded brief; in the other, the recorded brief with the change paragraph added. Both get the same confinement paragraph (E-001), with the copy's path. Both run on the same AI model, the model the operating model uses for that role when the kind's comparison opens, recorded with every run; both start within the same hour and within 7 days of the real dispatch.
- **Research (C3): one memo, two checks.** The memo is the real researcher's round-1 submission. The harness makes two copies of the commit the real check started from, and starts two source checks on the check's recorded model, one with the check's recorded brief and one with C3 added, within the same hour. Source checks may use the web, as the real check does; starting both together keeps the web the same for both as far as can be done.
- **Which arm is which** is hidden from every judge and from the owner: each arm's output gets a neutral label from a random draw whose seed is written into the result before the comparison opens.
- **The neutral export.** Each output to be judged leaves the work session only as its neutral export (S-001, J3): for plans and built work, a git bundle of two commits, the start commit's tree and, as its child, the arm's final tree, under one neutral author, date and message (the label), so no arm commit message or history reaches the judge; for research, a bundle of one commit, the tree at the memo's submission commit. The harness writes each export, its fill values and one index line under src/E-003/exports/<kind>/ in Model-Lab.
- **Nothing an arm writes leaves its copy** except as its export. No arm's output is merged into, pushed to or copied into any work repository. The real work goes on as it would have, unaffected.
- **No one sees outcomes early.** Verdicts are written, as pairs are judged, to the kind's verdict file in the sheets repository, which only the judging session holds; status reports and review points carry counts only, until the kind closes.

### Step 4 — judging (in the judging session)
- **The judging route** (S-001, "The judging route", J4 and J5). At each weekly wake of the judging session (S-001, "What wakes the long-lived sessions"), for each export in the kind's INDEX that has no line in the verdict file, the judging lead: reads the export from Model-Lab and checks its SHA-256 against its index line; reads `holdouts/<set id>.md` from its clone of the sheets repository and checks its SHA-256 against the fingerprint its brief gives, copied from governance/HOLDOUTS.md (a mismatch stops all judging); fills the judge brief with the Builder's fill script; makes a fresh copy from the export; starts the judge as a helper, with the copy as its working directory; applies the reruns (Sample); runs the transcript check on the judge; checks each cited path against the export's file list, writing `<n>@-` for one that names no file of the export (S-001, J5); and appends the judgement's line (J5) to `verdicts/<set id>.tsv` in the sheets repository, committed and pushed before the next judgement.
- **Plans and built work: two judge sessions per pair.** Each arm's deliverable is judged by its own judge session, on Fable 5.1, a different model from the doers' 5.5 line within the one provider the plan allows (docs/PROJECT.md section 8; the environment check). The judge's brief is E-002's judge-brief template (experiments/E-002.md, "The judge-brief template"), with the changes listed below, and the kind's held-back check given in full. The judge sees the deliverable (the range from the export's first commit to its second, in a fresh copy), never the arm's hand-back or commit messages, which could name the change. For built work, the harness also runs the project's locked checks for that stage in the arm's copy in the work session, mechanically; an arm passes only if the judge returns PASS and the locked checks pass.
- **Research: one judge session per memo.** The two arms are the two check versions' verdicts on the same memo, so there is one deliverable to judge: one judge session on Fable 5.1 judges the memo against the research held-back check, opening its sources. Each check version's verdict is then read with it (Measure).
- **Every change E-003 makes to E-002's judge-brief template.** Nothing else in the template changes; each filled brief is the same, byte for byte, for every judgement of the same output.
  1. `<checker role id>` and its role file: the critic (plans), the reviewer (built work) or the source-checker (research), the role file at the piece's start commit in the copy.
  2. `<piece id>`: the output's neutral label (Step 3), never the piece's own id or the arm.
  3. "Judge it against:" names the task statement: for plans, the task statement of the worker's recorded brief, given as text from the export's fill values; for built work, the spec the stage builds, at the start commit; for research, the question file the memo answers, at the memo's submission commit.
  4. Added after "Judge it against": "Apply this check:", then the kind's held-back check in full, and "The work fails if any test of this check fails."
  5. For research only, "do not use the web" becomes "use the web only to open the sources the memo cites" (Exclusions 2); plans and built work keep the template's bar on the web.
  6. The return paragraph's "each blocking finding as one numbered line citing file:line" becomes "then the numbers of the tests of the check that failed, each citing file:line" (S-001, J5).
  7. Added (finding 4 of reviews/E-001/reviewer.md): "Run every command in the foreground and wait for it to end. Do not start background tasks. Your last message must begin with the verdict line."
- **What stays in the judging session.** Filled judge briefs and judge transcripts are never committed, pushed or copied into any repository; only each filled brief's SHA-256 and the J5 line are recorded. When every export up to the INDEX's final line `last` has its line, the judging lead returns the closing block, a final counts block and the verdict file in full (S-001, J5); the owner passes it to the Orchestrator, which records it byte for byte as reviews/E-003/<kind>/verdicts.tsv.

### Step 5 — the owner's sample (after every pair of the kind is judged, before the analysis)
- **A card is one output**, never a pair: for plans and built work one arm's deliverable; for research one memo. It shows the task in one line, the output's path, and the judge's verdict with the numbers of the tests that failed and their cited lines; the check's text is not on the card, and the owner may open it in the sheets repository (`holdouts/<set id>.md`). It shows no arm label, and for research not the two check versions' verdicts. The question: "Should this work have gone back to its worker? Yes / No / Can't tell." **Yes** is FAIL, **No** is PASS, **Can't tell** is no answer.
- **What can be drawn.** Outputs are sorted into three groups (for built work, outputs whose locked checks failed are left out of all three, since no answer can pass them):
  - **G1, outputs that decide:** both outputs of every pair whose arms' verdicts differ (research: every memo on which the two check versions' counted verdicts differ);
  - **G2, passed:** outputs the judge passed, in pairs where both arms pass (research: memos both versions' counted verdicts pass);
  - **G3, failed:** outputs the judge failed, in pairs where both arms fail (research: memos both versions fail).
- **How many.** 8 cards: 4 from G1, 2 from G2, 2 from G3. A group with too few outputs gives what it has, and the shortfall is drawn from G1, then G3, then G2. So a judge that wrongly passes, wrongly fails, or wrongly splits pairs can each be seen; for plans, where both arms may rarely pass, the G2 cards move to the other groups.
- **The draw.** Each group lists its outputs in the dispatch order of their pieces, and within a pair by neutral label. One generator, Python's `random.Random(seed)` with the kind's seed written into the result before the kind opened, draws `sample(G1, k1)`, then `sample(G2, k2)`, then `sample(G3, k3)`, then any further cards one at a time with `choice` from what is left, in the order G1, G3, G2.
- **"Can't tell."** If fewer than 6 of the 8 cards are answered Yes or No, further cards are drawn, one at a time, until 6 are answered or 12 cards have been shown in all.
- **What an answer does.** It replaces the judge's verdict for that output. Each pair's class (n10, n01 or concordant) is then worked out again from its two outputs' verdicts; for research, each check version's counted pass is worked out again from the new verdict on the memo. Unanswered cards and undrawn outputs keep the judge's verdict.
- **The owner's time:** about five minutes a card, 8 cards (about 40 minutes) per kind as a rule, 12 at most.

## Measure
- **Plans and built work.** For each pair: n10 if the change arm passes and the no-change arm fails; n01 if the reverse; otherwise concordant. First-time pass rate per arm = passes / pairs. Gain = (n10 − n01) / pairs.
- **Research.** For each memo, a check version's verdict counts as a pass only when the held-back check also passes the memo ("a pass the held-back check does not confirm is not a pass"). n10, n01 and the gain are then as above. Reported beside it: **false passes**, memos a check version passes that the held-back check fails, for each version.
- **The judge's standing.** On the owner's cards: how many were answered, and on how many answered cards the owner disagreed with the judge, by group.
- **What the measure is.** The deciding pass is the held-back check's, judged on a different model: a stand-in for V1's first-time pass at the project's real check. The link between the two is not tested here.
- **Reported, not deciding:** each pair's real round-1 verdict, beside the arms' verdicts (how often the held-back judge agrees with the real check is reported, not tested); tokens, tool uses and time per run as each helper reports at return; the served model of every run; pieces left out, with their reasons; the results of the first-use checks (S-001, K1 to K7), as one `k<n>:` line each, in the forms S-001's J4 and J5 give.

## Sample
**Pairs per kind.** 60, for each kind: the owner ruled size A at the Build gate (decisions/questions/P-001-build-gate.md), from S-001's options (40, 60 or 100 pairs); this registration is frozen with that number, before any run.

**Review points, not a calendar limit.** No time limit is set: the owner ruled none for Build, with these review points (decisions/questions/P-001-build-gate-terms.md, term 8), as decisions/questions/P-001-time-and-limit.md ruled no fixed length for Discovery. Each kind has a review point 16 weeks after it opens, and the owner's token checkpoints (every 20 runs of each side, below) are review points too. At each, the owner is shown counts only: pairs collected and left out, runs and tokens used on each side (the judging side's from its lead's last counts block, S-001 J5), the power at the pairs collected (experiments/E-003/sizing.py), and the weeks to the target at the pace so far. The owner rules "go on" or "stop this kind now". A stopped kind is analysed on the pairs it has, with its power at that size stated. The stop is never by results: no one is shown an outcome before the kind closes.

**Order.** One kind after another (decisions/questions/P-001-worst-work.md): built work, then plans, then research, as the owner ruled (decisions/questions/P-001-build-gate.md; decisions/questions/P-001-build-gate-terms.md, terms 2 and 3). A kind's comparison opens when the previous kind's last pair is judged, with no overlap: no kind starts collecting while the previous is judged, and the kinds do not all collect from the start; they are analysed one after another.

**Runs.**
- One run is one helper session started for this test, whatever it does; a session that errors still counts. The work session, the sheet session and the judging session themselves (the Builder's and the two leads' own work), their scripts and the real work are not runs; nor are the owner's cards.
- Per pair: plans and built work 4 runs (2 doers, 2 judges); research 3 runs (2 checks, 1 judge). Per kind: 1 run for its held-back check, in the sheet session.
- **Two sides.** Doer and check runs are started and counted in the work session (the work side); judge runs in the judging session (the judging side). Neither side can see the other's count as it runs, so each keeps its own share of the reserve and the cap, below.
- **Reruns.** (a) A judge that ends without a verdict line gets, in the same session, one fixed message, the same for every judge: "Return your verdict now. First line: `Verdict: PASS` or `Verdict: FAIL`." If it still gives none, one new judge session is started with the same brief (1 run). If that gives none, the pair is left out and listed. (b) A set-up fault (a wrong commit fetched, a copy built wrongly, a brief that differs between the arms other than by the change text) found before judging: the pair is run again once, both arms (2 runs, or 2 checks for research). (c) A judge whose line was not pushed to the sheets repository before its session was lost (S-001, K5) is judged again once with the same brief (1 run). A held-back check lost with its sheet session is written again (Step 1). Nothing else is rerun.
- **Reserve:** 10% of a kind's planned runs, rounded up, for reruns. It is split at the kind's opening between the sides in proportion to their planned runs, the judging side's share rounded down and the rest to the work side: at 60 pairs, plans and built work 13 work-side and 12 judging-side of 25; research 13 and 6 of 19. When a side's share is spent, its next pair needing a rerun is left out and listed.
- **Hard cap per kind:** the planned runs plus the reserve, counted as started, the same totals as before the split; each side stops at its own planned runs plus its share. The Builder reports the work side's runs and tokens to the Chief of Staff at every 20 work-side runs; the judging lead stops at every 20 judge runs and returns its counts block only (S-001, J5), going on when the owner says "go on" (decisions/questions/P-001-test-budget.md).

## Exclusions
Each is listed in the result with its piece and reason; none is re-tried for a better answer.
1. **In-flight inputs** (reviews/E-001/reviewer.md, finding 8). A pair is left out when, between the start commit and the real work's round-1 submission, any file the brief or the task statement names changes on the project's default branch, or the real work's branch takes in a commit that is neither its own nor an ancestor of the start commit. The harness decides this from git, mechanically, before the pair is judged.
2. **Leaks.** An arm's transcript shows a tool call that reads, searches or runs a command on a path outside its copy, other than the system paths E-001's F4 allows and files the harness itself saved of that run's own output, at the path the harness named to it (the reading ruled on in reviews/E-001/reviewer.md, ruling 1, is settled here in advance), or a call that names the sheets repository. A judge's transcript shows a tool call that reads, searches or runs a command on a path outside its copy, other than those same system paths, or web use; the research judge may use the web only to open the sources the memo cites. Doer arms may not use the web; source checks may. Either leak leaves the pair out.
3. **Harness context differs** (finding 5). The harness records each arm's full starting context (its first transcript lines). Before judging, it compares the two arms': they must match except for the change paragraph and the copy path. A pair that differs otherwise is a set-up fault (Sample, reruns). The instructions file each arm is given is the copy's own repository's, never Model-Lab's or the Builder's; whatever the harness cannot remove must be the same in both arms, and is named in the result. For judges, the judging lead checks each judge's first message equals its filled brief byte for byte and records the result and the brief's SHA-256 only, since the context holds the check; a judge that fails it is a set-up fault (one new judge session, 1 run, from the judging side's reserve).
4. **No deliverable.** A doer arm that ends without the deliverable of its kind counts as a FAIL for that arm, not an exclusion: not finishing is part of the work.
5. **No verdict** after the reruns above.
6. **Not eligible** at entry (Method, step 2): no record at dispatch of the brief, start commit or model (for research, of the source check's); first found by the work session more than 7 days after its dispatch; no role file for C1's `<path>`; an empty list for C2 (experiments/E-003/C2-built-named-inputs.md, cases); the piece is from a repository that is not public; the piece belongs to this test.
7. **A served model changes mid-comparison.** Both arms of a pair always run on the same served model; a pair whose two arms report different served models is a set-up fault. If the served model changes between pairs, pairs are analysed by model, and the deciding test is run on the larger group only; the split is reported.

## Deciding threshold
Set now, per kind, after the owner's answers have replaced the judge's verdicts on their outputs:
- **Judge confirmed:** at least 6 cards answered Yes or No, and the owner disagreed with the judge on at most 2 of them. **Not confirmed** otherwise, with the reason (too many disagreements, or too few answered after 12 cards): no change is kept for that kind from this run; the result is "not shown: judge not confirmed", with the figures, and the owner rules whether to re-judge or stop.
- **Kept:** judge confirmed, **and** the one-sided exact binomial test on the discordant pairs gives P(X ≥ n10 | n10 + n01, ½) ≤ 1/40. For research also **the false-pass guard**: C3's false passes are no more than the unchanged check's plus one.
