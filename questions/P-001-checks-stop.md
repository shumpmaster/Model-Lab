# Ruling needed: how the fair test's checks go on after their reviews kept failing

Milestone: Build-1

The checks the fair test's work must later pass are written but have failed their reviews again, so Build has not moved. Two of them must test the list of files given to two sessions, the one writing the secret marking sheet and the one analysing the results, and both guess from a list's contents whether it is theirs; the last two versions of that guess each let a faulty list through as a pass. The worst case is a list that shows the session writing the secret marking sheet the test's own plan of changes. An independent trace found nothing else blocks, going by the review records. No rule says how many rounds checks get; this stop is applied as for plans and built work.

WHY: the checks cannot be used until their reviewers pass them, and using them despite a failed review is never an option; how they go on is yours to choose (Personal-Org-Operating-Model OPERATING_MODEL.md §4 "Stop rule"; docs/LEDGER.md holds no grant).
OPTIONS:
  The stop rule's four routes:
  A. One focused round — the checks' writer gives each of the two checks its own setting, so each tests the list it is named for, whatever that list holds; one review then runs every case in the trace's table, not only reads it, and a failure comes back to you. Gain: the trace finds this meets every case, and that the plan itself is not wrong, so by the Chief of Staff's reading no superseding entry is needed. Cost: the last two fixes to this part each opened a new hole, and the trace worked its cases by reading the code, not running it, so this round may fail too; how long, not estimated. Rules out: nothing. Reversible: yes.
  B. Re-specify — the plan's two joins are revised to say how each check is told which list is its own; changing the frozen plan "needs a superseding entry" (AGENTS.md §1), with its own plan review, then the two checks are rewritten. Gain: closes the gap the trace found in the plan itself. Cost: a plan review and a rewrite before Build moves, and the rewritten checks still need their reviews; how long, not estimated. Rules out: nothing. Reversible: only by a further superseding entry (AGENTS.md §1).
  C. Re-scope — the two checks stop testing the named lists, and each list is checked by hand instead (the trace's re-scope). Gain: no more rounds on this part. Cost: in the trace's words, "a weaker gate"; and since the plan's joins require those lists to be tested, it too needs a superseding entry (specs/S-001.md, joins J7 and J8). Rules out: a machine check of those lists. Reversible: only by a further superseding entry (AGENTS.md §1).
  D. Drop — the fair test stops and its registered experiment is not run (triage, summary). Gain: no further cost on the test. Cost: no tested result for any change, which the project's fourth milestone needs (docs/PROJECT.md, M4). Rules out: the test, until it is planned again. Reversible: only by planning it again.
RECOMMENDATION: A, with medium confidence (the Chief of Staff's judgement, following the trace): by the trace it meets every case, and by the Chief of Staff's reading it is the only route that keeps both the frozen plan and the test. Confidence is medium because the trace ran nothing, and reading-only reviews have already passed tests a correct build would fail (docs/LESSONS.md LL-60). What would change it: wanting the plan itself to say how a check is told its list (then B), or wanting no further rounds on this part (then C).
WHO HAS CHECKED IT: the Critic, on a different AI model from the writer; round 1 failed this card and round 2 passed the redraft (record: reviews/P-001-checks-stop/critic.md). The trace was a fresh session in the Critic's role, which flagged that it faults the Critic's own earlier rounds.
