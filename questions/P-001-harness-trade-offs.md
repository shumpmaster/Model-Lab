# Ruling needed: the fair test's leak check is stricter than its rules in some places and misses some routes; keep it as it is, or change it before the first runs

Milestone: M4, Build-3

You are asked two things about the leak check, the part of the test's scripts that decides whether a helper looked outside the copy of the work it was given: whether to keep the places where it is stricter than the written rules, and whether to close the routes it does not see. Nothing has failed or been changed, and no test run has been spent. In the fair test, each piece of work is done twice, with and without a change, in three batches, built work first; a leak by either helper throws the pair out for good. The stricter places cost pairs: a commit message or printed text that only mentions a path counts as a leak. The routes it misses could let a helper look outside unseen: a script it writes with its file tool and then runs, or a path its code builds. The scripts have used the three review rounds the rules give; changing them now takes another round, and only you can allow that. Either choice can be undone later, but pairs already lost stay lost. There is no default: this waits for you.

WHY: the check decides which pairs count, so it bears on the test's result; you ruled that any change to the scripts or the locked checks needs your ruling.
OPTIONS:
  Part 1, the stricter readings:
  A. Keep them, each listed in the result as a known limit. Gain: no further round. Cost: a hit in a helper's work throws its pair out with its 2 to 4 runs spent, never rerun; a brief naming a temporary folder loses its piece before any run; a hit while the hidden check a batch is judged against is being written voids that check, and the batch waits for your ruling. The rate is not measured for new built work: in 911 real calls of earlier work, commit messages and printed text never hit, and patterns in code hit on 4 lines of one transcript left out anyway; the Reviewer judges commit messages naming routes likely in the Service Desk's built work. Rules out: getting back pairs lost this way; a later change means batches judged by different rules.
  B. Narrow the plainest — a new builder makes text that is only printed or put in a commit message read clean, and makes `//` count as the root folder; a reviewer runs every case. The rest stay as in A: code reading system files or writing to the temporary folder, patterns in code, outside paths in text written to a file, a temporary file written by sed, a network listener, a merge of the work's own side branch, a brief naming a temporary folder. Gain: fewer pairs lost to the forms the Reviewer judges likely. Cost: a round past the three, which no record found says is or is not a new round, so your ruling decides; its size is not measured (the first build and its review took 355,075 and 245,508 tokens; the later, smaller rounds added about 120,000 and 36,000 for the builder and 102,000 and 24,000 for the reviewer, in sessions that had already read the work); the builder's own tests change; a fix to these readings once turned a clean real call into a leak. Rules out: nothing.
  Part 2, the routes it misses:
  C. Record them as known limits. Gain: no further round. Cost: a helper that reads outside its copy through a script it wrote with its file tool, or a path its code builds, is not caught, though its session holds the real projects; the Reviewer's view is that a false leak costs only a pair while a missed one costs the test. Rules out: nothing.
  D. Close the file-tool route — look inside such scripts as the check already does for scripts written through the shell. Gain: closes the route the Reviewer found more common for writing scripts. Cost: a round as in B (one round if both are chosen); test files holding a pattern or a system path then read as leaks, as two test files in the earlier work would, since neither option narrows the reading of patterns in code; paths built in code stay a limit. Rules out: nothing.
  Under every option the brief records keep the form the scripts read, "recorded: at hand-out, <date>", as all 40 such records already do; a record written otherwise loses its piece before any run. If you would rather the scripts read the date, that joins a round from B or D.
RECOMMENDATION: A and C, with low confidence (the Chief of Staff's judgement): the first batch counts the pairs the stricter readings throw out, with no further round, which no record found provides for; a leak by a missed route would not show in any count, so C rests on the helpers being told to stay in their copies and on the Chief of Staff's judgement, which no record measures, that such a leak is rare. What would change it: wanting the likely commit-message losses avoided from the start (then B), or weighing a missed leak above lost pairs (then D).
WHO HAS CHECKED IT: the Reviewer found each reading and route; the Chief of Staff ran the scripts on every case on a copy; the Critic checks this card.
