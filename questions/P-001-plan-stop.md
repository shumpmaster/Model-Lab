# Ruling needed: how the fair test's plan goes on after its fourth review failed

Milestone: M2, Design-5, Design-6

The plan for the fair test passed its review at the third round, but the last check before Design closes, which looks at whether the plan's parts fit together, failed it on four points. All four concern how the plan connects to the tools that start helpers and decide what each may read. First, the tools cannot yet hand the helper that writes the test's secret marking sheets (the one never told what is being tested) the reading list made for it. Second, no record says where those marking sheets are kept or how a copy is shown to be unchanged. Third, the helper that analyses the results cannot open the records it would need. Fourth, the plan's list of files to keep from that helper would, if used as written, also hide its own task sheet. The independent trace put these mainly down to one cause: no brief asked anyone to check the plan against those tools. It found that these four touch none of the test's thresholds, sizes or options beyond one file pattern, but it did not re-check the seven smaller points the same review raised (Triage, round 4). The rules stop work on the plan until you choose one of four routes below. One of them, dropping the test, cannot be undone within this project.

WHY: the plan cannot be frozen, and the Build gate cannot be put to you, until it passes its review; after a failure at the third round or later, the next step is the owner's choice (Personal-Org-Operating-Model AGENTS.md, "Plan stop rule"; OPERATING_MODEL.md §4, "Stop rule").
OPTIONS:
  A. One focused confirmation review — Gain: the plan as reviewed is kept, and only what failed is fixed. What happens: the plan's writer fixes the four points and three smaller ones in the same files (findings 5, 6 and 9, not blocking), and one review checks only those, given the tools' files this time. It needs a rule change you would approve separately: changes to the tools so that the secret-sheet writer can be given its own reading list, and so that the analyst can read the results, a named store and an unchanged-copy check for the marking sheets, and a ledger entry for any change to their record. Cost: not estimated. If that review fails, it comes back to you the same way. Rules out: nothing, but if you decline the rule change, the secret marking sheets cannot be written and A cannot succeed.
  B. Re-specify — Gain: the whole plan is rewritten and reviewed afresh, including the seven smaller points. What happens: a new draft, reviewed from round one. It still needs the same rule change as A, since the fixes to the tools sit outside the plan. Cost: not estimated; more rounds than A, since review restarts at round one. Rules out: nothing.
  C. Re-scope — Gain: no rule change for the secret marking sheets (the analyst's reading may still need one). What happens: the plan is narrowed, for example by dropping the secret marking sheets so that your own sample of the judges' verdicts is the only check from outside; a narrowed plan is a new draft, reviewed from round one. Cost: not estimated; a weaker test. Rules out: the secret marking sheets.
  D. Drop — Gain: no further work or runs on the test. What happens: the fair test is not run. Cost: no result on whether any change helps. Rules out: any answer to the question this project set out to test, unless a new plan is made later.
RECOMMENDATION: A — the four failures are in how the plan connects to the tools, and Triage found they touch none of the test's thresholds, sizes or options beyond one file pattern; A fixes what failed without restarting what passed. What would change it: declining the rule change (then C or D), or the confirmation review finding further gaps of the same kind (then B), or the Service Desk's standards being out of the secret-sheet writer's reach (then C, limited to this project's standards) (triage/P-001-S-001-round-4.md, "Options for the owner's card").
