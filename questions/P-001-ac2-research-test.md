# Ruling needed: one of the fair test's checks fails a correct build, and how it is corrected

Milestone: Build-1

One of the checks the fair test's work must pass is wrong, and no correct build can pass it. It tests that, for research, the two versions of the source check's brief differ by one paragraph only. But the plan gives each version its own fresh copy of the work and has each brief point at its own copy, so a second paragraph always differs too. The only way to pass it would be to leave the real work's location in the brief, which the plan forbids. The Builder found this and the Reviewer confirmed it by running it; every other check passes or is skipped by design. Nothing has been changed. The checks are now locked, and no rule says how a locked check is corrected, so you choose. The correction goes into a pull request that needs your own verdict, so nothing changes until you approve it.

WHY: the build cannot pass while this check fails, and accepting work despite a failed check is never an option (Personal-Org-Operating-Model OPERATING_MODEL.md §4, "Stop rule"). The model sends a wrong check back to the checks' writer (§4, "Feedback routing": "criteria or checks wrong → 3 or 4") but says nothing on changing a check after it is locked; the locked checks' own notes say they are "Never edited once locked; a new spec supersedes it" (tests/acceptance/e003_support.py:4). Leaving it unruled holds the Build's review from passing; the rest of the build goes on meanwhile.
OPTIONS:
  A. Correct this one check now — the checks' writer changes only this test, so it ignores each copy's own location before comparing, as the same file's built-work test already does; the Reviewer then runs every case of it, not only reads it; the change comes to you as a pull request needing your verdict, because the checks are a high-risk area. Gain: the smallest change, and the frozen plan is untouched. Cost: one round by the checks' writer and one review; how long, not estimated. Rules out: nothing. Reversible: yes, by a further change with your verdict.
  B. As A, and fold in the three minor points set aside on these checks — the wording of the note on files a run creates, how the scan of brief records is classified, and a missing test of the named-record path (reviews/51/reviewer.md, round 4; triage/P-001-S-001-checks-round-5.md, finding 2). Gain: one change instead of two. Cost: a larger change; the last fixes to these checks' record selection each opened a new hole beside them (docs/LESSONS.md LL-61). Rules out: nothing. Reversible: yes, by a further change with your verdict.
  C. A superseding plan first — the checks' notes' route: a new plan that extends the frozen one, with its own plan review and freeze, before the checks' writer changes the test. Gain: follows the checks' own note to the letter. Cost: a plan review and a freeze for a fault in a test, not in the plan, which the Builder and the Reviewer both found right on this point; how long, not estimated. Rules out: nothing. Reversible: only by a further superseding entry (AGENTS.md §1).
  D. Drop — the fair test stops and its registered experiment is not run. Gain: no further cost on the test. Cost: no tested result for any change, which the project's fourth milestone needs (docs/PROJECT.md, M4). Rules out: the test, until it is planned again. Reversible: only by planning it again.
RECOMMENDATION: A, with high confidence (the Chief of Staff's judgement): the fault is in the test alone, the fix copies what the same file already does for built work, and a small change keeps the risk of a new hole low; the three minor points stay set aside, as you asked. What would change it: wanting all known points on these checks closed in one go (then B), or reading "never edited once locked" as binding (then C).
