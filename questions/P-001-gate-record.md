# Ruling needed: how should your gate rulings reach the records the checks read, for work run from a conversation?

Milestone: M1, M2, M3, M4, M5, M6

WHY: Each project has automatic checks that block a change breaking the operating model's rules. They learn that you have approved a project only from a "status record", a small file the pipeline writes when its script, not a conversation, runs the work. This project has been run from a conversation with the Chief of Staff, so it has no status record, and the checks still treat it as not approved, although you passed its Design gate and accepted its first milestone, the count of past rework. Until that changes: no milestone can be marked reached; and the checks that require a review before an approved project's standard milestone lines are changed, and your ruling before work is dropped from them, do not apply. Changing what the checks read is a change to the operating model's rules, so it is yours; filing a hand-written record by-passes the rule that only the pipeline writes these records, so that too is yours.
OPTIONS:
  A. change the operating model so the checks see your recorded gate ruling — made in the operating model repository under its own rules (a written spec, its tools builder, an independent review, your merge), then copied into this project. The spec settles the route: either the checks read your recorded "proceed" ruling where no status record exists, or the pipeline's script writes the status record from that ruling. *Gain:* every project run from a conversation gets it, not only this one. *Cost:* how long it takes is not known; the first milestone stays unmarked until it lands. It does not by itself fix the related gap where the standard milestones and the timeline show "not recorded" for conversation-run work; that stays with the end-of-cycle changes. *Reversible:* yes.
  B. file a status record for this project by hand — written in the Orchestrator's name from your ruling, naming the fair test's spec. Every state such a record can hold has a side effect: "ready" and the working states make the pipeline's script start work on it; "waiting-owner" needs a card that does not exist, so the script rejects the record and logs an error, and your desk shows a false "waiting on you" item; "done" loads quietly, but your desk then shows the project as finished while it is in Design. *Gain:* the first milestone can be marked within the day, with no rule change. *Cost:* it by-passes the rule that only the pipeline writes these records, and whichever state is used, either the script or your desk is told something untrue; only this project gains. *Reversible:* the record can be deleted, but anything the script logged or did meanwhile stays in its log.
  C. leave it until the end of the cycle — the fix joins the other lessons that go into the operating model at the end (M5, M6). *Gain:* no work now. *Cost:* no milestone can be marked reached for the rest of the project, and the review-and-ruling protections on the milestone lines stay off. *Reversible:* yes.
  Under every option your acceptance of the first milestone stands: the mark is added, citing that ruling, once the checks can see the approval.
RECOMMENDATION: A, with medium confidence (the Chief of Staff's judgement): it fixes the cause for every conversation-run project, and keeps the status records honest. Confidence is medium because its time is unknown. What would change it: if showing the first milestone reached now matters more to you than a project page that wrongly reads "finished" until the change lands, B in the "done" state.
