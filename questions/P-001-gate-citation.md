# Ruling needed: how should the Build gate's case show you the plan's criteria, while the checks cannot open the plan?

Milestone: Design-6

The case for moving the prompt engine into Build is on hold. The independent check of the case found that it does not show you the criteria you would be approving, the budget options or the open questions, and that it carries too few risks. The risks, the budget totals and the open questions can be fixed as things stand. The criteria cannot: every line of a case must point to a record that the case's automatic check can open, and that check cannot open the plan. It finds a project's plan only through a record the automatic pipeline writes, and this project, run from our conversations instead, has none; your earlier ruling sent that gap to a change in the operating model, which has not been written yet. This asks where the criteria should be written for you meanwhile. Nothing here is irreversible.

WHY: the case is what you rule the Build gate on, and the criteria, as scenarios, are what the model says you approve there; until this is settled, the case cannot be reworked, and the gate waits (Personal-Org-Operating-Model OPERATING_MODEL.md §2 and §4 "Phase gates"; reviews/P-001/_build-gate-1-critic.md).
OPTIONS:
  Under every option, the case is held to about 350 words, so it can only summarise the eleven criteria and point to where they are written in full; the budget options' run and week totals are cited from the review of the plan, which the check can open; and the plan's open questions reach you on the terms card beside the gate, as now, which the case says. The options differ in where the full criteria are, and what the checks then say.
  A. the case points straight at the plan, and the check stays red on those lines — you read the criteria in the plan itself. The case's check refuses each such line ("not one the Critic's gate pack holds"), so the governance check on the gate's pull request stays red after your verdict on that pull request's other change, and runs red again on the default branch once it is merged, since that run checks the merged changes too; every later change to the case is red the same way. While the default branch's latest check is red, the pipeline's loop starts nothing and merges nothing, and after an hour it files a "CI hold" card for you; today that loop does not run in this repository at all (it stops at its token check, for want of a setting), so this applies only if it is set up while the red stands. Gain: the fastest; you read the plan's own text. Cost: you would merge past a red check, and a red that everyone knows about invites reading past red, as in lessons 29, 42 and 48; and the hold above, if the loop is set up. Whether GitHub lets you merge past a red check depends on this repository's settings, which I cannot read. Reversible: yes.
  B. the criteria are copied into the gate's "proposal" file beside the case, and the case points at that — you read the criteria there. The proposal is the one-page view the model writes for a user representative; here you are the user, so no representative reads it, and it is used only as a record the check can open. Its "How you would use it" section holds the plan's eleven criteria, and the check confirms that each line's words appear, word for word, in the line of the plan it names; it would not catch a criterion cut short, so I would copy each whole, and the gate Critic would be given the plan to check that, as it was last time. Gain: every check stays green, and the copy is checked against the plan. Cost: the criteria appear twice; the proposal is used for something it was not designed for, which the case says; the power figures appear in the review of the plan only in part, so they stay on the gate card, as now. The pipeline's script ignores the file: it acts only on the records it writes itself, and runs a user representative only for a project with a target-user profile, and this one has neither. Reversible: yes.
  C. the gate waits for the operating-model change — first the change your earlier ruling chose, so the checks see your recorded rulings, is specified, built, reviewed and merged in the operating model's repository, then copied here; it is meant to let the checks find this project's plan too, but no spec yet says so. Gain: the cause is fixed for every project run from a conversation, with no copy and no red. Cost: nothing has been specified yet, and the one plan now in that repository's queue has stopped twice in review; how long it takes is not known, and the gate, the plan's freeze and the test wait until then. Reversible: yes.
  The change in C stays owed under every option: your earlier ruling stands, and A or B only bridge this one gate.
RECOMMENDATION: B, with medium confidence (the Chief of Staff's judgement): it keeps every check green, the copy is checked against the plan, and the gate is not held for a change of unknown length. What would change it: if you would rather not see the proposal form used for something it was not made for (then A, if a red check is acceptable to you, or C, if the gate can wait).
WHO HAS CHECKED IT: the Critic, on a different AI model from the writer (record: reviews/P-001-gate-citation/critic.md; PASS at round 2).

DEFAULT: B   TIMEOUT: 72 hours
