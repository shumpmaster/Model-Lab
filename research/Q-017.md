# Research question — Q-017

*Drafted by the Chief of Staff; revised after the Critic's round 1 (reviews/P-002-research-q017/critic.md). Checked by the Critic for gaps and neutral phrasing (D-032, D-055).*

## The question

A small organisation does its work through AI agents, each started for one task, and one person, the owner, who reviews, decides and merges. Its work is kept in three git repositories, available locally at /home/user/Service-Desk, /home/user/Model-Lab and /home/user/Personal-Org-Operating-Model (on GitHub as shumpmaster/Service-Desk, shumpmaster/Model-Lab and shumpmaster/Personal-Org-Operating-Model). The commit history of each, as of 2026-11-09, is given to you as an extract in /home/user/Model-Lab/research/Q-017-extract/ (one JSON line per commit; its README says how it was made). Count, from the extract and the repositories' files, who made and merged the changes, how often the owner was asked to decide, how many rounds of checking each piece of checked work took, and how often merged changes were later reverted or changed again. Give every count at both ends (for example, with and without a commit by the owner).

1. **Units.** Count merged pull requests, per repository and per month. Class each by kind from its title and the paths it changes (built work, a plan or spec, research, records only, an owner question or answer, or other), with a stated rule; a pull request that fits two kinds is counted under each and flagged. Count separately the changes that reached the default branch with no pull request, as far as the extract shows; pull requests closed without merging are not in the extract. Give the number of changed lines as a second view beside each count.

2. **Who made and merged each change.**
   - Identities: the extract classes each commit's author as agent (an address ending in agents.invalid), owner (the GitHub account shumpmaster and the addresses it uses) or other, and gives author and committer names; addresses are left out. List the names in each class, and say how you treat merge commits, commits made through GitHub's web interface, and the "other" names.
   - For each merged pull request: the commits by agent identities, by the owner's identity and by others; and who merged it. GitHub records a pull request merge as a commit titled "Merge pull request #n", committed by GitHub and authored by the merging account. Give the shares at both ends, and the same counts at commit level.
   - Limit: an identity is not proof of who did the work. An agent session may commit under the owner's git settings, and work from before the agents.invalid convention began carries another identity. Say from what date the convention appears in each repository.

3. **Questions put to the owner.** The number of files added under questions/ and the number added under decisions/questions/, per month and per merged pull request, from file names and commit dates only. Say how a question file is matched to its answer file and how either is linked to a pull request. Use file names only to count and match; do not report them. Limit: a question file does not prove the owner was asked, nor an answer file who answered, and decisions given in conversation leave no file.

4. **Rounds of checking.** This is a recount on the same records as two earlier counts (research/Q-006-memo.md and research/Q-008-memo.md), extended to 2026-11-09 and linked to merged pull requests. Use these definitions:
   - a *piece* is one item sent to one kind of independent check: a plan to its review, a research memo to its source check, built work to its reviewer, an owner question to its critic, or a gate case;
   - a *round* is one recorded verdict on a piece by its checker; a round is identified by piece, checker and date, so a verdict recorded both in a pull request's verdict file and in a series round file counts once;
   - *passed at the first try* means the piece's first recorded verdict is a pass;
   - a piece *reached the stop rule* when three verdicts in a row on it are fails; any check after that (a focused, confirmation or deciding check) is counted as a round but reported separately;
   - a check added later to a piece that already passed counts as a new round of that piece, reported separately; a piece with no recorded verdict is counted separately.

   Records of rounds: the verdict files under reviews/, the round sections of research/*-source-check.md and research/*-entries-check.md, and Service-Desk's dispatch-log/, which for scripted items is the only per-round record, since their source-check files keep only the last verdict. Give pieces, first-try passes, rounds per piece, and pieces that reached the stop rule, per kind. Say where your figures differ from the two earlier counts, and which record decides it; open those two memos only for that comparison, after your own counts are made.

5. **Merged changes later reverted or changed again.** For each merged pull request, whether a later commit's subject reverts or names it, or a later pull request changes the same files, within 14, 30 and 60 days of its merge. Same files is a coarse test, since the extract has no line-level history; say so, and report the reverts and the naming separately from file overlap. Report each window. Leave out files that are edited in turn by design (logs, ledgers, digests, generated files, and the session and dispatch records), and list the files left out. Report separately pull requests merged less than 60 days before 2026-11-09, whose windows are not complete. This counts later changes; it does not judge whether the earlier change was at fault.

6. **What the records cannot show.** For example: decisions and approvals given in conversation; the owner's time; work dropped before any record; fixes that do not name what they fix; files with no recorded verdict; gaps in the dispatch log; and the limits named above.

Report every figure on equal terms; whether any figure is large or small is not for this memo to judge.

**What you may read.** The extract, and the three repositories' current files. You have no git or GitHub access; what is not in the extract or the files is a limit to state (for example, pull request reviews and comments, and pull requests closed without merging). You may not read: the contents of anything under questions/ or decisions/ (file names and commit dates only); docs/projects/ or docs/PROJECT.md; any ideas/ folder; sessions/chief-of-staff/; any file named *-notes.md; reviews/P-002-research-q017/ and any other file about this question, Q-017. The extract leaves out the subject of any commit that touches those records; other subjects may be read for classing.

Out of scope: outside literature, and any recommendation of what to change.

## The decision it serves

A described baseline of the organisation's own records: who makes and merges its changes, how often its owner is asked to decide, how its checked work fares, and how often merged changes are changed again.

## What each answer would change

Each count becomes a figure that later work can be compared against; a count the records cannot support is marked so, with what it would take to measure it; what the records cannot show is stated as a limit on any use of these figures.
