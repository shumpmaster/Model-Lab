## Where a piece's dispatch comes from (for the Critic's check, step 1)
S-002 ("What a touch is"): a piece's dispatch is the commit time of the first commit that adds the brief record named by the piece's `Agent-Session:` trailers; with none, the author time of the piece's first commit. extract.py reads each `Agent-Session:` value after removing a leading `session_<id>` and one `/` or `-`:
- **Model-Lab:** the rest is `<role>-<number>`; the brief record is `docs/briefs/<number>-<role>.md` (for a one-digit number, `docs/briefs/0<number>-<role>.md` when the unpadded file does not exist).
- **Service-Desk:** two kinds of record.
  - Control files: `reviews/<item>/_control/<n>-<hash>.json` (for a builder, `reviews/<spec>/_control/…`), format `session-runner-control/1`, written by the scripted loop at each dispatch; each holds the brief text, the `session` value the dispatched session's commits carry as `Agent-Session:`, the `role` and `dispatched_at`. A value of the form `<item>:<route>:<time>` (the loop's own patterns: item `[PQE]-<n>`, route `[a-z][a-z0-9-]*`) is linked to the control file whose `session` equals it. That file is the record; its role is the file's `role`; its time is the earliest commit time of a commit that adds the file (for a session with more than one control file, the earliest among them). As a cross-check only, the matching `"action":"dispatch"` line of `dispatch-log/<YYYY-MM>.jsonl` (same item, route and time) is found by its unique `prev` hash, and every value whose line's first-add time differs from the file's is listed in frames.json (17 in Service-Desk, all in frame D or outside the window: 16 differ by 1 to 6 seconds and one has no dispatch-log line).
  - Brief records: `docs/briefs/<task-id>.md` (its README: "One file per builder dispatch, `<task-id>.md`"). At the cut-off that folder holds only its README.
  - A value of the form `gha-<run>-<n>` is a GitHub Actions run and names no brief. Any other value is read as for Personal-Org-Operating-Model.
- **Personal-Org-Operating-Model:** brief records are `docs/briefs/<task-id>.md` (its README: "One file per builder dispatch, `<task-id>.md`"). Task ids are `s-<three digits>`, some with a suffix (for example `s-015-proof-brief.md`), and two others, `adopt-v3` and `adopt-v3-stamp`. A value holding `adopt-v3-stamp` or `adopt-v3` names that brief. Otherwise the brief is `s-<NNN>` from the value's first `s<NNN>` or `s-<NNN>` token; if text follows that token, the record is the longest `docs/briefs/s-<NNN>-<suffix>.md` whose suffix that text holds, else `docs/briefs/s-<NNN>.md`, and frames.json lists every in-window value whose text after the number matched no suffixed file (none). The role is the longest roster role name (builder, tools-builder, definer, critic, reviewer, researcher, source-checker, input-reader, check-author, release, coder, test-author, orchestrator, chief-of-staff, user-rep, design-reviewer) found as hyphen-separated words in the value; an abbreviation (`tb`, `def`) is not read as a role.
- A record's "first add" everywhere in this extract is the earliest commit time among the commits that add it, not the first in git's listing.
- A bare session value names no brief. In the window, most pieces' trailers are bare, so most dispatch times come from the first commit (frames.json and the M files' `dispatch_from`).

## Labels in place of paths and names
A file is written as its class by K1 (computed on the real path) and a label, the first 8 hex digits of the SHA-1 of its full path; a head branch as its role prefix and the same kind of label of its full name; a question or decision file as a label of its path. The same file always has the same label.
