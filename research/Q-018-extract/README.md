- **How each pull request merged.** For every merged pull request in the three repositories, the default branch holds a two-parent merge commit committed by GitHub whose second parent is the pull request's head commit as GitHub's record gives it (all 498 pull requests merged in the three repositories by the time the list was read: 103, 340 and 55). - **Reviews, owner comments and frame U's closing accounts** are read from GitHub for the pull requests the sample draws and for every frame U pull request, after the draw (reviews.jsonl, written then). - Pull requests closed unmerged after the cut-off, and open pull requests, are in no frame.

## Where a piece's dispatch comes from (for the Critic's check, step 1)
S-002 ("What a touch is"): a piece's dispatch is the commit time of the first commit that adds the brief record named by the piece's `Agent-Session:` trailers; with none, the author time of the piece's first commit. extract.py reads each `Agent-Session:` value after removing a leading `session_<id>` and one `/` or `-`:
- **Model-Lab:** the rest is `<role>-<number>`; the brief record is `docs/briefs/<number>-<role>.md`.
- **Service-Desk:** two kinds of record.
  - Control files: `dispatch-log/<YYYY-MM>.jsonl`, one JSON line per event, written by the scripted loop. A value of the form `<item>:<route>:<time>` (item `Q-<n>` or `P-<n>`) is the loop's session for the line of a dispatch-log file with `"action":"dispatch"`, that item, that route and that time. That line is the record; its role is the line's `role`; its time is the commit time of the first commit that adds the line (found by the line's unique `prev` hash).
  - Brief records: `docs/briefs/<task-id>.md` (its README: "One file per builder dispatch, `<task-id>.md`"). At the cut-off that folder holds only its README.
  - A value of the form `gha-<run>-<n>` is a GitHub Actions run and names no brief. Any other value is read as for Personal-Org-Operating-Model.
- **Personal-Org-Operating-Model:** brief records are `docs/briefs/<task-id>.md` (its README: "One file per builder dispatch, `<task-id>.md`"), where a task id is `s-<three digits>`, sometimes with a suffix (for example `s-015-proof-brief.md`). The brief named by a value is `s-<NNN>` from its first `s<NNN>` or `s-<NNN>` token, and its record is `docs/briefs/s-<NNN>.md`; a suffix in the value is not matched to a suffixed file. The role is the longest roster role name (builder, tools-builder, definer, critic, reviewer, researcher, source-checker, input-reader, check-author, release, coder, test-author, orchestrator, chief-of-staff, user-rep, design-reviewer) found as hyphen-separated words in the value; an abbreviation (`tb`, `def`) is not read as a role.
- A bare session value names no brief. In the window, most pieces' trailers are bare, so most dispatch times come from the first commit (frames.json and the M files' `dispatch_from`).

## The sample, the seed, the cut-off, the order and the edge-case table (S-002 step 2, unchanged)
2. **The sample.** *Window:* from 2026-10-01 00:00 UTC up to, not including, the cut-off, 2026-11-12 00:00 UTC (the start of the day this change to the spec was written), whatever day the extract is built; a pull request is in the window by its merge time (frame M) or close time (frame U), and a commit by its author time (frame D); "at the cut-off" below means at that moment. *Frames:* (M) the pull requests merged in the window; (U) the pull requests closed unmerged in the window; (D) the commits reachable from a default branch, with an author time in the window, that are in no merged pull request's own commits that GitHub's record does not give as a merged pull request's merge or squash commit, and that are not among the commits a rebase merge adds (for a pull request merged by rebase, the commit GitHub's record gives and the commits before it on its first-parent line, as many in all as the pull request's own commits), local merges included; in a repository whose GitHub records are not read, or where that walk back cannot be made, such commits cannot be told from work with no pull request, so its frame D commits are listed as "untested" for E-RP1. *Random part, 60, from frame M:* 20 from each repository. In Service-Desk and Personal-Org-Operating-Model, 10 from those whose 30 days after merging have passed at the cut-off and 10 from the rest; in Model-Lab, whose first merged pull requests are in November (research/Q-017-memo.md §1), 20 from all. A stratum with fewer than 10 gives all it has, and the rest of that repository's 20 comes from its other stratum; a repository with fewer than 20 in the window gives all it has, and the shortfall is listed, not made up from another repository. All merged pull requests are drawn from, pieces or not, so rule RP2 is tested. *Drawn how:* each list is put in the order of the SHA-256 of `<seed>:<repository>:<pull request number>` (for frame D, `<seed>:<repository>:<commit hash>`), lowest first, and the first are taken; the seed is the fixed string `S-002-handcheck`, and the repository is written by its name as in rule RP1 (`Personal-Org-Operating-Model`, `Model-Lab` or `Service-Desk`), so the order for a pull request is that of the SHA-256 of, for example, `S-002-handcheck:Model-Lab:12`. *Edge-case part, up to 2 per sampled case:* for each case the table below marks as sampled, the first 2 in its frame, over the three repositories together in the same order, not already drawn, that match its filter; a case with no match is listed as "not seen". The cases the table marks as not sampled have no filter a no-text extract can apply; the Critic checks them from the records as the table says (step 5). *Why 60, 20 each:* 60 is the size of the starting count; with 20 from a repository, a rule that fails on 1 in 10 of its pieces is seen at least once with chance 1 − 0.9^20, about 0.88.

## The fields (S-002 step 3, unchanged)
3. **The extract's fields** (no subject, title, message, comment or path text; one file per repository and frame). *Per pull request of frames M and U:* repository; number; created, merged and closed times; merged or not; the merging or closing account's class (owner, agent, bot, other); the head branch's role prefix only (`build/<role>/`, `orch/`, other) and a label of its full name (the first 8 hex digits of its SHA-1, as in research/Q-017-extract/README.md), so that branches match without names; its dispatch time and what gave it (brief record, control file or first commit). *Per commit:* hash; author class; committer class (GitHub web editor, agent, bot, other); author and commit times; whether it carries an `Agent-Session:` trailer, and that trailer's role and brief number; its `Spec:` trailer's spec id; whether its subject starts "Revert", and the commit hashes its message names after "This reverts commit"; the pull request numbers its subject names. *Per changed file:* its class by K1 (computed by the Orchestrator on the real path, which is not written), its status, its added and removed lines. *Per review:* reviewer class, state (approved, changes requested, commented, dismissed) and time. *Owner comments:* the counts on the pull request and on its lines, each before or after merging. *Per brief whose work it carries (by trailer):* its role, whether its brief record exists, and the commit time that first adds the record. *Questions and decisions:* each question file and each decision record (top-level `questions/` and `decisions/`) that names the pull request, with the commit time that first adds it. *First check (C1):* the record kind found (Critic plan review, Reviewer, Source checker, none), the first round's verdict (PASS, FAIL or none found) and its number of rounds. *Closed-unmerged matches (RT3(b)):* for each pull request of frame U with the same head-branch label or a shared brief number, its number, closing account class and closed time. *For the 30 days after merging:* later merged pull requests sharing a file (Q-017 §4's left-out files left out), later commits naming its number, reverts naming it or one of its commits (RR1(a)), and review records with a `Reopens:` line naming it; whether its 30 days are complete at the cut-off. *Per commit of frame D:* hash, number of parents, author and committer classes, author and commit times, its trailer's role and brief number, and its files' classes and lines. *Per repository:* whether GitHub's records were read ("read" or "not read"; if not read, frame U and the review and comment fields are absent and recorded "untested", above).

## The files
- **<repo>.M.jsonl:** one line per pull request of frame M, oldest merge first: repository, number, created, merged_at, closed, merged; merge_commit (hash); merging_account_class; head_prefix and head_label; dispatch and dispatch_from; briefs (per brief by trailer: brief, from, role, record_exists, record_first_added; a Service-Desk control line is given as `control:<label>`); commits (the pull request's own commits: reachable from its head and not from the merge commit's first parent), each with the per-commit fields; files (the union over its commits, each with label, class by K1, status set, summed added and removed lines); questions_decisions (each top-level `questions/` or `decisions/` file in the same repository, first added on the default branch by the cut-off, whose text as first added names the pull request by S-002's naming rule: label, kind, first_added and which part of the rule matched: number, brief, spec or path); first_check (each C1 record found at the cut-off: kind, for which kind of work, the first round's verdict and its number of rounds); rt3b_matches; after_merge (the 30 days after merging, read up to the cut-off: later merged pull requests sharing a file, with Q-017 §4's left-out files left out; later default-branch commits whose subject names its number; reverts naming it or one of its commits; review records in any of the three repositories with a `Reopens: <repository>#<number>` line for it; days30_complete).
- **<repo>.U.jsonl:** one line per pull request of frame U: as above, with its commits (reachable from its head and not from the default branch at the cut-off) and its briefs; closing_account_class is filled after the draw.
- **<repo>.D.jsonl:** one line per commit of frame D: the per-commit fields with its files' classes and lines.
- **frames.json:** per repository, the default branch at the cut-off and the size of each frame.
- **sample.json:** the drawn sample, written by `python3 -I -B extract.py draw <this folder>` after the Critic's check of this README.

## Labels in place of paths and names
A file is written as its class by K1 (computed on the real path) and a label, the first 8 hex digits of the SHA-1 of its full path; a head branch as its role prefix and the same kind of label of its full name; a question or decision file as a label of its path. The same file always has the same label.

## How extract.py applies K1, and the readings it makes
- Rules 4 to 12 of research/Q-017-memo.md §1 are its script's `kind()`, applied to real paths.
- Rules 1 to 3 read Q-017's labels as the real paths its extract.py gave each label: a question or decision file is one under top-level `questions/` or `decisions/` only (S-002 K1 change (i)); a path under `sessions/chief-of-staff/`, under `docs/handoff/`, ending `-notes.md`, or containing `chief-of-staff` is records; a path under `docs/projects/` or `ideas/`, or `docs/PROJECT.md`, at any depth as Q-017's script labelled them, is plan.
- K1 change (ii): in Personal-Org-Operating-Model, the top-level `OPERATING_MODEL.md` and any file in a `playbooks/` folder are built. Its archived and proposal copies are classed by the twelve rules.
- Q-017 §4's left-out files are its script's `by_design()` list, applied to real paths.
- A commit's committer is "GitHub web editor" when GitHub (noreply@github.com) committed it; agent for an agents.invalid address; bot for a `[bot]` name; other for anything else (for example a tool's default identity). Author classes are Q-017's: agent, owner (the owner's account or configured address) and other.
- "Later commits naming its number": a default-branch commit within the 30 days whose subject holds `#<number>`, other than the piece's own merge commit. A number may be an issue's or another repository's.
- Question and decision files are searched in the piece's own repository only, in their text as first added.
